# 设计稿与 UI 开发规范

本目录是 Live2D 桌面伙伴 App 的**视觉事实来源**。任何设置页、桌宠聊天框、对话气泡或外部消息测试台的新增、重构和视觉修复，都必须先选定本目录中的参考图并完成风格锁定，再进入开发。

现有代码、`README.md` 和 `docs/` 仍是功能、真实文案、数据、安全和 Electron 平台约束的事实来源。设计图未展示某项功能或状态，不代表可以删除它。

本目录只用于开发与视觉验收，`package.json > build.files` 已排除 `设计稿/**`，图片和本说明不会进入正式应用包。

## 1. 设计稿分组

| 分组 | 用途 |
|---|---|
| `主设计稿.png` | 三种方向的总览与整体气质参考；不是局部尺寸或控件状态的最终依据 |
| `玻璃质感主题-*.png` | 玻璃主题的角色、行为、AI、系统、聊天框及局部细节 |
| `二次元治愈主题-*.png` | 治愈主题的角色、行为、AI、系统、聊天框及局部细节 |
| `对话框气泡/` | 两种主题下玻璃、甜美、像素、科幻气泡及长消息状态 |
| `外部消息测试台/` | 消息调试、消息历史与 API 文档三个页面 |

同一功能存在多张图片时，开发前必须把实际采用的文件逐一写进风格锁定，不得只写“参考设计稿”。

## 2. 参考优先级

从高到低依次为：

1. 用户在当前任务中明确指定的图片、主题和变更说明；
2. 同主题、同区域的局部或详细设计图；
3. 同主题的完整页面设计图；
4. `主设计稿.png` 的总体方向；
5. `design-demos/`、现有 UI 和历史截图，仅用于补齐前四项没有表达的信息。

高优先级来源覆盖低优先级来源。若同级设计互相冲突、目标主题不明确或缺失会影响整体风格的关键状态，必须请用户确认，不能凭习惯选择。

## 3. AI 开发的风格锁定门禁

AI 在修改任何 UI 源码之前，必须实际打开相关图片进行视觉检查；只根据文件名或文字描述推断不算完成。随后在任务回复中先输出以下记录：

```text
风格锁定
- 开发范围：页面、组件和状态
- 目标主题：玻璃质感 / 二次元治愈 / 外部消息测试台
- 参考文件：逐项列出设计稿相对路径
- 视觉锚点：布局、层级、颜色、字体、圆角、边框、阴影、材质、图标和装饰
- 保留行为：现有交互、真实文案、数据与平台约束
- 待确认项：冲突、缺图或无法从静态图确定的行为
- 验收计划：需要复现并截图的主题、页面、状态和窗口尺寸
```

门禁规则：

- 风格锁定未完成，不得先写 HTML、CSS、Canvas 绘制或替换视觉资产。
- 目标清楚且设计无冲突时，AI 可在记录风格锁定后继续开发；存在实质歧义时必须暂停并等待用户确认。
- 用户在开发中更换主题、参考图或范围后，原锁定自动失效，必须重新锁定。
- 单个主题内可以复用结构与行为，但玻璃和治愈主题的颜色变量、材质、插画与装饰必须隔离，禁止混搭成第三种风格。

## 4. 视觉提取清单

风格锁定至少检查以下内容：

- **画布与结构：** 窗口比例、内容顺序、网格、边距、留白、滚动区域和固定区域。
- **层级与材质：** 背景、玻璃透明度、模糊、卡片或连续分区、边框、高光和阴影关系。
- **色彩与字体：** 主色、强调色、状态色、标题/正文/说明文字的层级、字重、行高和对比度。
- **控件与状态：** 导航、按钮、输入框、滑杆、开关、卡片、徽标的默认、悬停、焦点、选中、禁用、加载、错误和空状态。
- **角色与装饰：** 角色图层、品牌 Logo、猫爪、星光、手写签名、背景插画的来源、裁切、层级和透明度。
- **内容边界：** 长文案、长路径、长消息、小窗口、系统缩放和滚动时的溢出策略。
- **动态与可访问性：** 过渡节奏、减少动态效果、键盘焦点、文字可读性和足够的状态区分。

## 5. 实现约束

- 先还原信息层级、几何关系和阅读顺序，再处理光效与装饰；不能用更多阴影或渐变掩盖结构偏差。
- 主题值应通过现有主题作用域或 CSS 自定义属性集中管理；禁止为追图在组件内部散落互相矛盾的硬编码颜色。
- 优先复用仓库中的真实 Logo、角色和主题资产。不得用 Emoji 充当正式图标，也不得用 CSS/SVG 临时画假角色替代真实资产。
- 不引入通用深蓝 SaaS、青紫霓虹、卡片汤或无依据的“AI 风格”作为缺省方案。
- 设计图只决定视觉和明确展示的交互，不自动授权修改 IPC、持久化、模型加载、安全设置或窗口行为。
- 若受 Electron、透明窗口、Live2D 渲染或可访问性限制无法原样实现，应记录限制、给出最接近方案，并取得用户确认后再偏离。

## 6. 视觉验收门禁

UI 任务只有同时满足以下条件才算完成：

1. 在目标窗口尺寸、目标主题和与设计一致的内容状态下生成实现截图。
2. 将实现截图与本次锁定的设计图并排或叠加检查，至少核对布局、间距、尺寸、字体层级、色彩、圆角、边框、阴影、透明度、图片裁切和滚动边界。
3. 检查设计中未完整展示但产品需要的交互状态，确保没有因视觉还原而丢失功能或可访问性。
4. 执行 `npm run check`、`npm run lint`，并按影响范围运行 `npm run qa:settings`、`npm run qa:chat` 或 `npm run qa:external-message-ui` 等定向 QA。
5. 在交付说明中列出使用的设计稿、验证过的页面/状态，以及所有有意偏离和原因。不得用“基本一致”替代具体对照结果。

纯逻辑改动若完全不改变布局、样式、文案、可见状态或视觉资产，可以不做新的风格锁定；一旦影响用户可见结果，就必须重新执行本流程。
